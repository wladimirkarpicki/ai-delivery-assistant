feat(monitoring,security): expose real Prometheus metrics, harden /api/health

The monitoring stack was decorative. monitoring/prometheus.yml has always
scraped /metrics, but the app had no such route: the SPA catch-all
answered with index.html, so Prometheus recorded zero samples and every
dashboard and alert was built on nothing.

- add GET /metrics returning Prometheus exposition format, counted per
  scrape from the ledger: aida_projects, aida_meetings,
  aida_history_events, aida_open_risks, aida_open_blockers,
  aida_open_action_items, aida_open_items_total. Verified live: the
  endpoint now answers text/plain version=0.0.4 with real values instead
  of the SPA document. No bearer token, because the scrape config cannot
  authenticate and the payload is counts, not content.

- harden GET /api/health. It was unauthenticated and returned the model
  name plus the raw provider error, which confirmed the vendor, the exact
  model and whether the API key was configured. It now returns
  analysis_ready plus a stable reason code. The frontend contract is
  updated to match: HealthInfo carries reason instead of model/error, and
  AddMeetingPage maps the code to operator copy.

- get_available_models caches failures with a 60s TTL. Every
  unauthenticated /api/health call forced an outbound provider request,
  so a flood of them could burn the app's own quota and then take down
  add-meeting for authenticated users.

- ensure_item_embeddings no longer commits. It runs inside the caller's
  meeting transaction, so committing persisted a meeting whose analysis
  had not been applied yet; a later rollback then left a "ghost" meeting
  that also blocked re-submitting the same notes through the duplicate
  guard.

- catch SQLAlchemyError alongside ValueError and RuntimeError on the
  meeting write path. SQLite does not enforce varchar(n), so a too-long
  value from an LLM or a long upload filename only fails on a real
  PostgreSQL, where it was a 500 instead of a 400.

- project_memory: clamp strings to the width of the column they are
  written into, and normalize item status onto open/resolved/completed.
  An unrecognized status was silently excluded from the reports and the
  resolution-rate metric, so a project with stranded items reported 100
  percent resolved.

- monitoring: dashboards, an alert rule file, and the compose mounts for
  both. The dashboards state the endpoint and JSON keys they would need
  rather than inventing application metrics.

Tests: 77 increased to 78. New tests lock in the Prometheus format (and
that /metrics is not the SPA), the health response shape, and that health
discloses no vendor, model or key state.
