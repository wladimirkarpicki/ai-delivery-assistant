perf(api): bound the activity timeline to a 24-month window

month_counts read every Meeting and HistoryEvent row into Python on each
/api/metrics request. HistoryEvent gains a row on every event of every item
of every meeting, so the read grew for the life of the database and the
cost of the endpoint grew with it. The timeline itself renders a bounded
set of months, so the query now matches.

The bound is a datetime comparison rather than a dialect-specific date
function, because the tests run on SQLite and production on PostgreSQL, and
strftime and date_trunc each exist in only one of them.

Tests: 92 increased to 93. ActivityWindowTests seeds a meeting and its
history event 60 months old plus a recent one, then asserts the recent month
is in the timeline and the old one is not, which is the regression that
would otherwise have been invisible: the old behaviour returned both and
still looked correct.

Also records in SECURITY.md that token revocation is in-memory and does not
survive a restart, with the bound being the token's own TTL, and that the
timeline window is deliberate. Both were previously undocumented, so the
first looked like a feature and the second like an accident.
